## 二、真卡与无卡怎么分

- 默认 `pytest` 只跑**不依赖真卡**的用例（配置里的 `-m 'not realcard'` 干的）；
- 真卡用例标 `@pytest.mark.realcard`，在带卡机器的宿主栈容器内用 `pytest -m realcard` 跑；
- 当前真卡用例只有 1 个函数 × 3 套栈 = 3 条：`tests/tiering/test_offload_realcard.py`，验
  「栈能真导入 + connector 类能取到 + 新旧路径取到的是同一个类」。

**为什么这么分**（写进 `tests/README.md`，不是洁癖）：组里有人在没有国产卡的机器上改池本体，
单测默认要卡等于他们没有单测可跑；本包刻意零依赖，四家容器的 torch / vLLM 版本互不兼容，CI 里
装不出一套「正确」的；三套卸载栈在同一环境里只有一套能导入成功，拿 CI 去 import 它们必然两套失败，
失败原因还和代码对不对无关。

### 三类各举几条（都是在测真实存在的东西，不是空壳）

**正常**
- 能力查询返回已声明能力：L0 八项在 L0-only 后端上 `has(...) is True`，L1 四项 `is False`；
- 降级查表对「缺内存句柄」给出**张量级池**路径，且该路径对象就是 `DEFAULT_IMPLEMENTATION_PATH`；
- 分层门禁脚本在**本仓当前干净树**上退出码 0，输出里有「门禁通过」与两条规则名；
- 兼容别名取类时**先发** `DeprecationWarning`，警告文案里有 `0.3.0` 与新路径；
- 句柄申请返回的五个公共字段齐全，释放后在世句柄数归零、已用字节归零。

**边界**
- **L1 能力在声明与未声明两种后端上的分支走法**：同一句 `alloc_handle(1024)`，声明句柄的后端
  返回句柄、未声明的后端抛 `CapabilityNotDeclared`（池就是靠这个分支决定走不走句柄形态）；
- 假后端显存三键的**零值**（`total=0` 时三键全 0）与**满值**（申请满后 `free=0`，再申请一字节
  必须报显存不足，不许透支）；
- 能力分级的边界：四级家数 4/3/2/1；真有界同步按家数属 L3 但用法是 `BRANCH`；
  「有界同步」与「真有界同步」是两项不同能力；四级互不重叠且覆盖全部枚举；
- 别名包取不存在的属性抛 `AttributeError`，且**不发**弃用警告（否则日志会被噪声淹掉）；
- 缺一项 L0 就判 `core_path_ready is False`，并报出缺的是哪一项；
- 门禁的管辖边界：`tiering/offload` 里的 `import torch` **不算**违规（误判它等于把改造做反）；
  `torchless` / `my_torch_helper` / `vllmish` 这类名字像但不是框架的模块不误伤。

**异常**
- **调用未声明能力必须报错而不是静默退化**：`CapabilityNotDeclared` 带得出是哪项能力、哪个后端，
  文案里有「不得静默退化」并指向降级表；另有一条专门断言它「不许返回 None/0/False 假装成功」；
- 事件未 record 就查询 / 同步 → `EventNotRecorded`（不变量二）；
- 二次释放、释放非本层句柄 → `DoubleFree`（不变量一：厂商行为四家相反，池自己记账拦）；
- 有界同步超时返回 `False` 而**不是**抛异常（降级路径三：超时不等于失败）；
- **门禁脚本遇违规 import 必须非零退出**：用临时目录造违规样本（**不污染仓**）—— 顶层 `import torch`、
  `import torch_npu`、`from vllm.config import ...`、`import vllm_ascend`、`import vllm_fl`、
  `import torch.nn as nn`、能力层里的框架 import、**函数内的延迟 import**、
  `import_module("torch")` 字面量、`__import__("vllm")` 字面量、池依赖 `tiering`/`profiling`、
  池用相对 import（`from ..tiering import offload`）绕上去、多处违规全部列出且逐条带行号、
  语法坏掉的文件也拦住。

## 四、持续集成

`.github/workflows/ci.yml`，`push` 与 `pull_request` 触发，矩阵 Python **3.10**（对齐
`requires-python = ">=3.10"` 的下限）与 **3.12**，`fail-fast: false`。三步：

```yaml
- run: pip install -e ".[dev]"
- run: python tools/check_layering.py
- run: pytest
```

**CI 不装 torch / vLLM，不碰真卡。** 理由同第二节：装不出一套「正确」的版本，而池本体与能力层
本来就不许碰框架 —— 无框架环境正是它们该跑的环境。

## 六、对使用方的影响

- **改池的人**：改完先跑 `python tools/check_layering.py` 再跑 `pytest`，两条都绿才提交。
  本机没装 pytest 可以 `pip install -e ".[dev]"`；不想动全局环境就
  `uv run --with pytest python -m pytest -q`。
- **无卡成员**：默认那 114 条全都能跑，不需要任何芯片、不需要 torch / vLLM。
- **带卡机器**：进宿主栈容器后 `pytest -m realcard` 验三套栈的真导入（一次只有一套会过，
  另两套的宿主栈版本不同 —— 这是设计，不是失败）。
- 别名包的用例对宿主栈在不在都成立：在位则断言取到类，不在位则断言「警告先发出 +
  `ModuleNotFoundError`」，**不用 skip 绕过**。

## 七、留给后续的口子

1. **池的业务实现还没有，所以没有池的功能用例**。分级块池 + 流有序分配是 11-28 的出口，
   那批实现落地时同批补用例（正常/边界/异常三类同样要齐）。11-28 判据里「一款芯片实测通过」
   那部分要进 `realcard` 那一档。
2. **CI 只在 ubuntu-latest 上跑**。组里的机器是 Linux 容器，暂不需要 Windows 档；本机
   （Windows + Python 3.13）是手跑验的。
3. **没有覆盖率门槛**。当前被测代码就是协议与查表，覆盖率数字没有参考意义；等池实现落地再定阈值。
4. **CI 没有 lint / 类型检查**。`ruff` / `mypy` 要不要加、加哪一套，等池实现落地一起定，
   现在加等于先给一个只有协议的仓立规矩。
5. **真卡用例只验了导入面**。卸载栈的真实行为仍靠实测证据覆盖（那批数据的处置归第 3 件改造）。
