## 二、搬到哪

接收端 = 公共协作仓 `FlagRT/runtime-team` 的 `dev/memory/`，**沿用该目录的既有习惯，分两处落**：

| 内容 | 落点 | 为什么是这里 |
|---|---|---|
| 结果报告（PLAN / RESULT / 通俗版） | `dev/memory/docs/goals/<批次目录>/` | 该目录就是方向的结果报告处，`proto-910c-202609` / `proto-910c-202610` / `proto-p800-202610` / `proto-ppu-202610` 已是既有结构，10-23~10-26 四批的报告本来就在里面 |
| 原始数据（json / log / txt / 腿本 sh / 探针 py / 预注册锚） | `dev/memory/evidence/flagmemory-offload/<批次目录>/` | **新建目录**。理由见下 |

**为什么新建 `evidence/`**：`dev/memory/` 的既有习惯是「报告入仓、原始数据不入仓」
（`.gitignore` 里 `benchmarks/out/`、`docs/goals/proto-p800-202610/README.md` 原话
「原始数据在本地与服务器归档，按组内惯例未入仓」）。ADR-0014 §3.1 把该目录职责改为
**继续承载实测证据**，所以原始数据第一次需要一个入仓位置，既有结构里没有。
按任务书给的命名建 `evidence/flagmemory-offload/`，一级限定「哪条线的证据」，
将来池本体的对照数据另起一个一级子目录，不与卸载线混。

**批次目录名保持原样**（`p800_results_1025` / `p800_results_1027`），不改名。
理由：报告正文里有大量形如 `proto_lock/ON_pass2/chain.log`、`p800_results_1025/proto/S2-r2-OFF.json`
的证据引用，保留批次名使换算只是加一段前缀，不必逐份改报告正文（报告是冻结的证据文档，不动）。

## 三、索引怎么用

本仓留 **`reports/INDEX.md`**（旧 `reports/README.md` 用 `git mv` 改名）。
**改名理由**：该目录已不含报告，只含一份指针表；`INDEX.md` 在组内就是「指针表」的意思
（指挥台与各级目录同名文件均为此用途），叫 `README.md` 会让人以为目录里有报告。

索引内容按「不翻代码仓就知道证据在哪、覆盖了什么」的要求写了四节：

1. **批次索引表**：每批次 = 测期 + 芯片与栈 + 验证了什么 + 结果报告路径 + 原始数据路径；
   三批「无原始数据条目」的明写无，免得有人去找不存在的目录。
2. **覆盖面一句话**：三款国产芯片、各自四步闭环、哪两款另有真模型与规范级执行。
3. **怎么引用**：引用须带公共协作仓的**提交哈希**（证据追加式，只认提交不认分支）；
   报告正文相对路径的换算指到接收端 README 的换算表；附只取 `dev/memory` 的稀疏检出命令
   （公共协作仓在 Windows 上全量检出会撞文件名长度上限）。
4. **本仓纪律**：实测数据不回流，新证据进公共协作仓、本索引加一行。

接收端也各留了说明：`dev/memory/evidence/flagmemory-offload/README.md`（批次一览 +
文件命名约定 + 引用与复核）、`dev/memory/docs/goals/proto-p800-202610/README.md`（补了
10-27/28 三行 + 「原始数据」一节的路径换算表）、`dev/memory/STATUS.md` 的「交付物指针」
段补一行指向证据目录。

### 5.2 为什么地址行不参与任何判据

该行是引擎初始化时打印的分布式后端连接串，**不是任何判据的数据来源**。本批证据的判据量取自
逐腿 JSON 字段、DMA marker 账本与引擎日志中的池结算行，与这一行无关。为此逐项重算做了前后对照
（输出见 7.7），四类复核量**一字未变**：

| 复核量 | 取自哪里 | 前后 |
|---|---|---|
| marker 行数（4 份账本） | `*marker_transfers.txt` 行计数 | 1,195 / 1,324 / 1,638 / 6,296，不变 |
| 池 token 数（4 份 P 腿 JSON） | `pool_tok` / `pool_log_line` | 466,032 ×4，不变 |
| DMA 账本 total（6 份账本） | `dma_ledger-*.json` 的 `total` | 全部不变（含 ON pass2 的 1,247 批/202,388 块、pass1 的 1,316 批/202,415 块、OFF 全零） |
| 全等率素材（6 份 L 腿 JSON） | `rounds[].records[].text_sha1` 计数 | 250×4 / 216×2，带 `text_sha1` 者与总数相等，不变 |

另取**全部 249 份 json 的字节流聚合 sha256** 作旁证：
`82d9d8ae99820c46b6900cd51403489120522fabc4d894479348710a4e22368b`，前后相同——
脱敏只碰了 7 份 `.log`，数据本体一份没动。

### 5.3 既存泄漏那 1 处：只改当前文件，不改 git 历史

公共协作仓 `dev/memory/docs/goals/proto-p800-202610/RESULT_诊断与四步闭环_P800昆仑_20261023.md`
第 46 行的 `/home/<账号>` 换为 `/home/<用户>`，其余字节一字不动。

**口径（总组裁定）：只改当前文件，不改 git 历史。** 理由如实记下：改当前文件只减少**此后**的曝露，
历史提交里那个字节仍在，任何人检出旧提交都还能看到；要彻底清除须改写已共享的 `dev-1.0` 历史，
会让所有人的检出失效，**总组不主动做**。

这份文件是本仓「只删不搬」那 8 份副本之一：**本仓那份随搬迁一并删除，不需要脱敏**；
要脱敏的是公共协作仓里已存在的那一份。

### 5.4 纪律：公开仓 ⇒ 证据入仓前必须过泄漏核查

`FlagRT` 下的仓是**公开仓**，往这些仓推证据等于公开发布。所以：

**任何实测证据入仓前，必须先过一遍泄漏核查，核完才允许 `git add`。** 核四类：
IPv4 地址 / 主机名与用户家目录路径 / 账号形态 / 口令与密钥形态。
命中就先脱敏再入仓，不要先推了再想办法——推上去那一刻就已经公开，事后脱敏只能止损，删不掉历史（见 5.3）。
可见性未知时按**最严一侧**办（一律脱敏），不按宽松一侧假设。

   所以 `.gitignore` 只拦得住「形态」，拦不住「内容」——证据入仓前必须按 5.4 的四类
   核一遍（地址 / 主机名与家目录 / 账号 / 口令与密钥），核完才允许 `git add`。
   命中先脱敏再入仓；可见性未知时按最严一侧办。推上去才发现只能止损，删不掉历史。
