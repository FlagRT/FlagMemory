## 一、改了什么

三件事：**把池向下要用的后端能力面写成协议**、**给无卡环境一个假后端**、**加一个静态门禁把规矩钉住**。

### 1. `flagmemory/caps/` 落五个模块（纯标准库，零框架依赖）

| 文件 | 内容 |
|---|---|
| `capabilities.py` | 能力枚举 `Capability`（16 项）+ 分级 `CapabilityLevel`（L0/L1/L2/L3）+ 池的用法 `PoolUsage` + 三条写死的不变量文本 `POOL_INVARIANTS` |
| `backend.py` | `DeviceBackend`（`typing.Protocol`，池向下要用的能力面）+ `MemoryInfo` / `MemoryHandle` + 三个异常 |
| `degradation.py` | 五条降级路径 + 查表函数 `degradation_for` / `degradation_plan` / `missing_capabilities` |
| `query.py` | 能力查询入口 `has` / `require` / `report`，`CapabilityReport` 给出声明·缺失·分级·降级计划 |
| `fake.py` | 纯内存假后端 `FakeBackend` + 四家的能力声明预设（单测与无卡环境用） |

能力分级的事实照抄 `inbox/调研-四芯片显存能力对照与池抽象分级-20261103.md` 第五节，**本次不重新论证**。

### 2. 分级与用法分成两件事（这是本次唯一一处对调研稿的建模补充）

调研稿的四级分法是按**声明该能力的芯片家数**分的。直接拿级别当「池能不能用」会出一处错：
「真有界同步」按家数只有昇腾一家（属 L3），但它不是「只作诊断增强」的东西 —— 缺它要换回收屏障
的实现（降级路径三）。所以每项能力另带一个 `PoolUsage`：

- `CORE_PATH` —— L0 八项，核心路径直接用；
- `BRANCH` —— L1 四项 + 真有界同步，走能力分支，缺则按降级表；
- `FORBIDDEN` —— 设备上下文生命周期（L2），池绝不自建上下文；
- `DIAGNOSTIC_ONLY` —— 厂商数值错误码表、设备级真重建（L3 另两项），只作诊断增强。

**L0 的「有界同步」与「真有界同步」是两项不同的能力**，不是一项。混成一项就会在除昇腾外的三家上
写出阻塞等待。

### 3. 协议的命名口径

内存句柄沿用统一后端接口的五个公共字段 —— 句柄号 / 种类 / 后端名 / 设备序号 / 字节数
（`handle_id` / `kind` / `backend` / `device_index` / `nbytes`）。两个待加字段 **用途标签**
`purpose`、**所属流** `stream_id` 按「可选、缺则按最保守处理」先占位，等 11-25 与设备方向联合冻结
后对齐改名。**厂商指针不进句柄**：协议里没有 `ptr` / `address` 一类字段，并有用例钉住这一点。

池向下要用的口共九个：显存三键查询、取流、比流、建事件、record、query、有界同步，以及**可选**的
句柄申请 / 释放。

### 4. 两条沿用统一层的纪律写进了协议

- **能力如实声明**：后端用 `declared_capabilities()` 报它实测具备什么；
- **未声明的能力被调用时报错，不得静默退化**：抛 `CapabilityNotDeclared`。
  调用方看到异常才去查降级表，而不是靠「返回了个空值」去猜。

### 5. 三条不变量在协议层就有拦法

| 不变量 | 协议/假后端里的拦法 |
|---|---|
| 回收不依赖厂商报错 | 句柄登记表自己记账；重复释放与非本层句柄抛 `DoubleFree` |
| 事件判完成不许裸调查询 | 对未 record 的事件查询 / 同步一律抛 `EventNotRecorded`，绝不返回「已完成」 |
| 池持有流必须强持有 | 假后端的流对象刻意不做任何弱引用自动清理；协议文档里写明池强持有 |

### 6. 分层门禁脚本 `tools/check_layering.py`（纯标准库，不依赖 pytest）

检两条规则：

- **规则 1**：`flagmemory/pool/**` 与 `flagmemory/caps/**` 里不许 import 推理框架与厂商运行时
  （禁止名单 15 个顶级模块：`torch` `torchvision` `vllm` `vllm_fl` `vllm_ascend` `vllm_xpu`
  `torch_npu` `torch_mlu` `torch_xmlir` `acl` `acllite` `cnrt` `cndev` `bkcl` `hccl`；新增芯片
  往名单里加，不许在代码里加例外）；
- **规则 2**：`flagmemory/pool/**` 不许 import `flagmemory.tiering` 与 `flagmemory.profiling`
  （依赖方向只许向下）。

**用 `ast` 静态扫描，不靠 import。** 两个理由：门禁机器上没有 torch，真 import 会把「违规」和
「环境没装」混成一种失败；静态扫描还能抓到**函数内的延迟 import** 与
`importlib.import_module("…")` / `__import__("…")` 的字面量 —— 那是藏框架依赖最常见的两种手法。
相对 import（`from ..tiering import offload`）也会被解成绝对模块名后判。

用法 `python tools/check_layering.py [仓根]`，违规逐条打印 `文件:行号 + 违规 import + 原因`，
非零码退出。接受仓根参数是为了让单测能在临时目录里造违规样本，不污染仓。

## 二、`tiering/offload` 侧：框架绑定只在这一层（已核过）

**核过一遍，结论是现状本来如此，本次未改动那一层的任何代码。** 用 `ast` 扫全仓 `*.py` 找禁止名单里
的顶级 import，命中 15 个文件：

- 14 个全在 `flagmemory/tiering/offload/{npu,ppu,xpu}/` 下（`connector.py` / `*_worker.py` /
  `*_mem_ops.py` / `*_copy_backend.py` / ppu 的 `manager.py` `metadata.py`），用的是 `torch` 与 `vllm`；
- 1 个在 `reports/p800_results_1027/kit/probe_meminfo.py` —— 那是实测证据包里的探针脚本，不是包代码
  （`reports/` 的处置属第 3 件改造，本次不动）。

`flagmemory/{pool,caps,interfaces}/**` 与 `flagmemory/profiling/__init__.py` 零命中。

## 三、判据怎么对上

| 判据 | 对上的东西 |
|---|---|
| 池本体不得 import 推理框架 | `flagmemory/pool/**` 当前零框架 import；由门禁规则 1 静态把关，并有 14 条异常用例造违规样本验它真能拦 |
| 框架绑定下沉为可选适配层 | 框架 import 全部且只在 `flagmemory/tiering/offload/**`（第二节实查）；该层不被 `pool` 依赖（门禁规则 2） |
| 池本体只依赖设备方向统一后端接口 | 池向下只经 `flagmemory.caps` 的 `DeviceBackend` 协议取能力；协议的句柄字段与两条纪律沿用统一层口径，不自建第二套声明 |
| 核心路径只许用四家齐备的那级能力 | L0 八项 `PoolUsage.CORE_PATH`；L1 与真有界同步走分支；L2/L3 其余两项禁用或仅诊断。`CapabilityReport.core_path_ready` 给出「L0 不齐 ⇒ 这款芯片不该起池」的判读 |

## 四、五条降级路径落位

| # | 缺什么 | 池改怎么做 | 表里的键 |
|---|---|---|---|
| ① | 统一内存句柄（寒武纪 MLU590） | 退张量级池，只管分级/归属/归还账本，不碰裸指针。**同时是四家通用的默认实现路径** | `tensor_level_pool` |
| ② | 设备上下文生命周期 | 绝不自建上下文；归属校验走只读观测，寒武纪只靠池自己的登记表 | `no_self_context` |
| ③ | 真有界同步（除昇腾外三家） | 回收屏障「超时上报 + 轮询」，不阻塞等待，**超时不等于失败** | `timeout_report_and_poll` |
| ④ | 厂商数值错误码表 | 异常分级靠错误文本规则，沿用统一层那套，不自建 | `error_text_rules` |
| ⑤ | 设备级真重建 | 压力回收只做进程内回收，设备级故障只上报不自救 | `in_process_reclaim_only` |

`DEFAULT_IMPLEMENTATION_PATH` 指向第 ① 条 —— 它不是「出了问题才走」的降级，是默认形态；句柄形态
是声明了该能力的三家上的优化路径。

按四家预设算出来的降级计划：昇腾档 0 条、平头哥档 3 条、昆仑芯档 4 条、寒武纪档 5 条。

## 六、对使用方的影响

- **池的实现方**：向下只许经 `flagmemory.caps` 拿能力，核心路径先 `require` L0；L1/真有界那几项
  先 `has` 再决定走不走，不要拿 `require` 当分支判断（那是用异常做控制流）。
- **三套卸载栈**：一行没改，启动命令与 `kv_connector_module_path` 不变。
- **要接真芯片的人**：实现 `DeviceBackend` 协议，在 `declared_capabilities()` 里如实声明，
  未声明的口抛 `CapabilityNotDeclared`。禁止名单在 `tools/check_layering.py` 顶部，新增芯片往
  名单里加。
- **包版本不变**（0.2.0）：只加了池内部用的协议与工具，对外接口面没变。

## 七、留给后续的口子

1. **真后端未写**。本次只有协议 + 假后端。对接设备方向统一后端接口的真实现是后续任务；
   四家各一个后端的真卡复验也在那一步。
2. **协议字段名待对齐**。`MemoryHandle` 的五个公共字段按调研稿与接口诉求稿的中文描述起的英文名，
   **没有照着 `dev-1.0` 的 `dev/device-context/prototype/runtime/backends/base.py` 原文核过**
   （本次工作在 FlagMemory 仓内，没取公共仓那份源文件）。11-25 联合冻结接口文件时须逐字段核一遍，
   不一致就以设备方向的为准改这边。
3. **`purpose` / `stream_id` 两个字段是占位**，用途标签的六类枚举（权重/KV 缓存/激活/通信缓冲/
   临时工作区/未声明）本次**没有**落成枚举类型 —— 它要和设备方向一起冻结，提前写死会制造第二份
   会漂移的真相。协议里先用 `str | None` 透传。
4. **`interfaces/` 还是空的**。接口头文件目录的内容属 11-12 设计文档与 11-25 接口冻结的产物。
5. **SDK 原语面四项事实仍未取证**（虚拟地址预留+物理页映射、流有序分配原语、跨进程共享句柄、
   对齐与分配粒度常量，见调研稿第四节）。协议按「厂商无原生流有序分配原语」设计，探测到有再作为
   优化路径接上。
6. **门禁只管 `pool` 与 `caps` 两个包**。`interfaces/` 与 `profiling/` 目前没纳入规则 1 —— 前者
   是空的，后者的探针本来就要碰框架。等 `interfaces/` 有内容时应把它加进规则 1 的管辖范围。
