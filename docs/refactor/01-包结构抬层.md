# 改造说明 01 · 抬一层包结构

> 依据：ADR-0014（显存池组件落点定为 FlagMemory 独立仓）§3.5 第 1 件改造。
> 分支：`xliu969/pkg-layering`（个人分支，合入 `dev-1.0` 前四件改造须全做完）。
> 状态：✅ 已完成（导入面验证见第五节；三套栈的真实可用性须在带卡机器的栈内复验）。
> 合入 `dev-1.0` 的前提是四件改造全做完，本件是第 1 件。

## 一、改了什么

顶层包从 `offload`（18 条交付条目里的一个子线）改为按池组件分层的 `flagmemory`，五块：

| 包 | 职责 |
|---|---|
| `flagmemory/pool/` | 池本体：块分级、流有序分配，分配/复用/回收/碎片四类操作 |
| `flagmemory/caps/` | 芯片能力抽象层：能力查询与降级分支，对接设备方向统一后端接口 |
| `flagmemory/tiering/` | 分层存储；三套 KV→Host 卸载栈在 `tiering/offload/{npu,ppu,xpu}` |
| `flagmemory/profiling/` | 性能分析工具与探针（`probes/` 脚本集不入 wheel） |
| `flagmemory/interfaces/` | 对外接口声明（接口头文件目录） |

本次只建结构与占位：`pool/` `caps/` `interfaces/` 里只有 `__init__.py`（写明该层职责与硬约束），
**没有写池的实现** —— 池的最小可运行实现是单独一条出口。

## 二、新旧路径对照

| 旧 | 新 |
|---|---|
| `offload/npu_offload/` | `flagmemory/tiering/offload/npu/` |
| `offload/xpu_offload/` | `flagmemory/tiering/offload/xpu/` |
| `offload/ppu_offload/` | `flagmemory/tiering/offload/ppu/` |
| `offload/probes/` | `flagmemory/profiling/probes/` |
| `offload/README.md` | `flagmemory/tiering/offload/README.md` |
| module path `offload.npu_offload` | `flagmemory.tiering.offload.npu` |
| module path `offload.xpu_offload` | `flagmemory.tiering.offload.xpu` |
| module path `offload.ppu_offload` | `flagmemory.tiering.offload.ppu` |
| 导出类名 `Npu/Xpu/PpuSimpleCPUOffloadConnector` | **不变** |

ppu 栈内部 8 处绝对 import（`from offload.ppu_offload.X import ...`，分布在 `connector.py` 3 处、
`ppu_worker.py` 3 处、`manager.py` 1 处、`ppu_copy_backend.py` 1 处）改为相对 import。
npu/xpu 两栈本来就是相对 import，已核过无需改。

## 三、兼容别名与有效期

仓根 `offload/` 保留为**兼容别名包**，覆盖三个旧模块路径：

- **有效期：0.2.x 一个版本，0.3.0 移除。**
- 取类时发 `DeprecationWarning`，文案指明新路径与移除版本。
- 别名包与三个别名子包**不做无条件 import**，走模块级 `__getattr__` 懒加载。原因：三套栈
  各绑一个宿主栈版本，同一环境里只有一套能导入成功，无条件 import 会把另两套的
  `ImportError` 带给调用方。
- 存在的唯一理由：容器与启动脚本里已写死的 vLLM 参数
  `kv_connector_module_path=offload.<栈>_offload` 不必跟着改。vLLM 的 connector 工厂是
  `getattr(module, kv_connector名字)` 取类，懒加载的 `__getattr__` 正好接住这种取法。

## 四、依赖方向（本次钉下的规矩）

```
interfaces ← pool ← caps          池本体与能力层都不碰框架
tiering.offload → pool / caps     适配层可以向下用，反向不行
```

- **池本体不得 import 推理框架**（vllm / torch_npu / 各厂商 plugin）；框架绑定只许出现在
  `tiering/offload` 的适配层里。
- 顶层 `flagmemory/__init__.py` 不 eager import 任何子包 —— 池本体必须在无框架、无真卡的
  环境里可导入，单测与分层门禁都依赖这一点。
- 这条规矩本次只写进文档与各层 `__init__` 的约束说明，**门禁脚本与单测属第 2/4 件改造**。

## 五、验证（已跑，输出如实照录）

```bash
# 1 五层骨架在无框架环境可导入（本机无 torch/vLLM，正是要验的）
python -c "import flagmemory, flagmemory.pool, flagmemory.caps, flagmemory.interfaces, \
flagmemory.tiering, flagmemory.tiering.offload, flagmemory.profiling; print(flagmemory.__version__)"

# 2 别名包本身可 import；取属性时才触发栈依赖（无 vLLM 环境下取属性失败属预期）
python -c "import offload, offload.npu_offload, offload.ppu_offload, offload.xpu_offload; print('alias ok')"

# 3 全量字节编译
python -m compileall -q flagmemory offload
```

实际输出（本机无 torch / vLLM，Python 3.13，2026-11-03）：

```
layers ok 0.2.0
alias pkg import ok
compileall ok
```

第 2 条要验的是「失败发生在取属性时、import 别名包本身不报错」，不是「取属性成功」。单独验过：

```
import alias: ok
getattr raised: ModuleNotFoundError | No module named 'torch'
warnings: [('DeprecationWarning', 'offload.npu_offload 是兼容别名，0.3.0 起移除；请把 kv_connector_module_p…')]
unknown attr -> AttributeError: NoSuchThing
```

即：别名包与别名子包本身可 import；取 connector 类时才触发宿主栈依赖（无框架环境下如实报
`ModuleNotFoundError: torch`，预期）；取类同时发出 `DeprecationWarning`；取不存在的属性
按 Python 约定抛 `AttributeError`。**三套栈的真实可用性要在带卡机器的栈内复验，本机只能验到
「导入面与别名转发正确」这一层。**

## 六、对使用方的影响

- 装过 `pip install -e .` 的机器：重装一次（包结构变了，`include` 从 `offload*` 变为
  `flagmemory*` + `offload*`）。
- 只用 PYTHONPATH 的机器：PYTHONPATH 仍指仓根，不变。
- 启动命令：旧 `kv_connector_module_path` 字符串在 0.2.x 内不用改；要改的话照第二节对照表，
  类名不变。
- 包版本 0.1.0 → 0.2.0。
