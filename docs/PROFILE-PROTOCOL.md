# PROFILE-PROTOCOL.md —— 显存画像/卸载对照测定规范（v0.3，2026-10-25）

> 适用：memory 方向一切真机测定——显存画像、KV 卸载开关对照、OOM 防护验证、pip 功能包验收。
> 每条规则都有一次真实翻车做凭证（标注出处）；新增规则必须同样带凭证入册。
> 偏离本规范不可怕，不声明才可怕：每份报告末尾必须附"本轮偏离规范之处"。

## 0. 四条核心原则

1. **差分唯一**：对照腿与基线腿之间只允许差一个变量。其余（引擎史、池数字、
   prompt、卡）必须同位或逐字一致。
   〔凭证：P800 A/B 2026-10-24——两腿引擎史同位、池 466,032 逐字一致、token 真值全等，
   "快 38%"才立得住〕
2. **暖跑配对，冷跑只做 sanity**：同引擎至少两轮同负载，取第二轮；跨引擎冷跑
   不得用作 A/B 结论。
   〔凭证：P800 冷跑方差 ±70%（111-214s 全噪声），暖跑收敛 39.4 vs 40.4s〕
3. **数字五要素**：栈 + 芯片 + 卡况（独占/共卡）+ 冷暖 + 池口径。缺任一不可比、
   不可并列、不可进报告。
   〔凭证：FL 池减半 + block128 vs block16——跨栈比百分比必错〕
4. **有效判据先行**：开机前，每条腿必须先写下两行——"这个数字支持什么结论"和
   "达不到什么条件即为无效数据"。无效数据不入报告正文（附录可留，标"无效"）。
   〔凭证：2026-09 vllm-ascend 画像——输出 16-64 tok 的 decode 行、池利用率 6.2%
   的"并发压测"推上了 dev-1.0，数字本身成立但撑不起任何结论；本条即为此补〕

## 1. 环境锚点（每份测定开头）

- image vN / env vN（ENV-SPEC 六事实）/ 仓 commit / 容器名 / 卡号 / 测定起止时刻。
- 引擎版本三元组：vLLM 核心版本 + 插件（vllm-ascend / vllm-plugin-fl）版本号+短 hash。
  〔0.0.0 与 0.2.0 行为差异巨大（启动门槛修复、decode 未修），只写"FL 栈"不够〕

## 2. 查卡与占卡

- **空闲/占用唯一真值 = 容器内驱动查询**（`torch.cuda.mem_get_info` 及 NPU 等价物）。
  xpu-smi / npu-smi 双向会骗人，只做参考不做判据。
  〔凭证：xpu-smi 三次说谎——报 0 实隐 53.6G、报 65G 实为空卡、2026-10-24 报 65GB/98%
  vs 真值 95.97 free〕
- 测定起止各记一次邻卡状态（谁在跑、哪几张卡）；独占判定写进锚点。
  〔凭证：4B 上午 0.8 tok/s = 共卡污染 17×，独占复测 13.4〕
- gmu 闸遵守宿主机规则；实际足迹 ≪ gmu×total 时降 gmu 合法（要写明）。

## 4. 池画像（腿 P：静态，无生成负载）

**目的**：得到池的物理常数，供后续所有腿做容量推导。

- **配置**：按 §3 起服务，**零生成请求**。"无负载"指不起任何 completion 请求；
  服务自身 warmup 产生的静态占用照记（稳态 HBM = 就绪后 10 分钟采样均值）。
- **测**（全部来自引擎日志行/metrics，禁止手算）：
  1. GPU 池 token 数（启动行 "GPU KV cache size"）；
  2. block size（启动行/metrics）；
  3. 权重占用 = gmu×total − 池字节 − workspace（或按栈既有口径）；
  4. 稳态 HBM（smi 仅参考，标注不可信）；
  5. 最大并发 = 池 tok ÷ 4096（推导值，标注"口径"）。
- **有效判据**：池 tok 必须来自引擎日志原文；缺失该行的引擎版本不得出池数字。
- **产出**：本腿数字是 §5-§7 所有负载推导的分母。

## 5. 单流腿（腿 S：prefill + decode 基线，逐项定档）

### S1 prefill（TTFT 档位）

**目的**：纯 prefill 时延曲线。**结论边界**：只回答 prefill 时延，不回答吞吐。

- 定档（输入 token 数，用 /tokenize 校准 ±10%）：**256 / 1024 / 3072** 三档；
  每档 max_tokens=**1**（TTFT≈prefill，decode 干扰最小化）。
- **每轮必须冷 prompt**：轮 r 档 L 的请求号 i = r×7919+L（唯一）——同 prompt
  第 2/3 轮是 prefix cache 命中，测的是缓存查询不是 prefill。
  〔凭证：2026-10-25 规范验证跑——S1 v1 三档全 0.1s，即此坑〕
- 轮次：每档 3 轮全计（每轮各自是新 prefill）。
- **有效判据**：三档中任一档输出 >1 tok 即该档无效（decode 混入）；prompt 实际
  tok 数偏离目标 >10% 即无效。

### S2 decode（单流速度）

**目的**：单流 decode 稳态速度（决定"能不能用"的那位数）。

- 定档：输入 **256 tok**，max_tokens=**512**。
- 轮次：暖跑后 3 轮，报中位数 + 最差值（最差值防抖动掩盖）。
- **有效判据**：completion_tokens ≥ **128** 才算 decode 测量；**<128 tok 的
  decode 数字一律不得写出**——16 tok 的"速度"被调度抖动淹没，是噪声不是数据。
  〔凭证：2026-09/10 矩阵输出 16-64 tok 的行——这正是"测了跟没测一样"的形态〕
- 产出须带：tok/s、s/tok、输出 token 数、是否 chunked-prefill 交错。

**腿序是判据的一部分**：P → S → B 串行执行，重载腿（饱和档）之后不得接测
轻量腿（引擎从满载态恢复期间数字失真）。
〔凭证：2026-10-25——S1 重跑紧跟 c125 满载腿，256tok TTFT 8.2s vs 1024tok 2.2s 倒挂〕

并发腿 prompt 长度必须留余量：目标 = max_model_len − max_tokens − **128 tok**
（prompt 头部注入请求号带来的位数方差可达数 token，压线必炸 400）。
〔凭证：2026-10-25——c28 首跑 19/28 请求 400，成功者恰为 ≤3968 tok 者〕

## 6. 批量腿（腿 B：并发档位，每档开多少由池子算出来，不许拍脑袋）

**目的**：容量曲线——从几路并发开始，系统从"流畅"变"排队/饱和"。
"并发档位"= 一组从小到大的并发数，一级一级试上去，每档记一次系统状态
（排队了吗、池用满了吗），试完就知道分界线在哪一级。

- **每档并发数怎么定**（除法，不是猜）：设单请求 KV 足迹 = F tok（满长口径
  F=4096），第 k 档并发数 = round(该档目标池占比 × 池tok ÷ F)。四档目标池占比
  = **25% / 50% / 90% / 110%**（110% 故意超池，是测卸载价值的那一档）。
  例：池 466k、F=4096 → 28 / 57 / 102 / 125 路。
  〔反例凭证：拍脑袋定 c64，池 466k 下 64 路只占池 6%——卡没热就收工，
  "一切正常"等于没测〕
  每档 max_tokens=**128**。
- **有效判据（每档独立判定）**：
  1. 报告时必须同时写当时**池利用率峰值**（metrics kv_cache_usage_perc 或块账）；
  2. 利用率 <30% 的档只能标"未饱和参考"，**不得用于容量/饱和结论**——这就是
     6.2% 池利用"压测"的教训；
  3. 宣称"饱和/排队"的档必须出现 capacity waiting>0 或驱逐>0，否则视为
     "没压到"，负载加码重测。
- **有效判据（decode 侧）**：同 §5 S2——每请求输出 <128 tok 的批量行不进 decode
  结论，只进排队/容量结论（TTFT、完工时间仍有效）。
- 轮次：每档 2 轮取第二轮（首轮 sanity）。

## 7. 对照腿（腿 A/B：开关对照，唯一差分）

- 基线腿 = §5-§6 同配置（对照项=关）；对照腿唯一差分 = 目标开关（如
  kv-transfer-config 有无）。其余逐字一致（原则 1）。
- 负载两级（沿用 §6 推导）：
  - **cost**（≤池 50%）：回答代价。**预期判据**：差值≈0。注意：connector 的
    store 策略可能积极（低于满载也发生 store DMA），"无 DMA"不成立，"无代价"
    才是判据。〔凭证：2026-10-25——24% util 档仍有 store，但 c28/57/102 差值≈0〕
  - **expand**（池 105-115%）：回答收益。**有效判据**：关腿必须出现 capacity
    waiting>0（或驱逐>0），开腿必须有 DMA 计数（store/load 分开）+ 单批块数 +
    host RSS 起止 + 完成归还检查——缺任一，"收益"结论无效。
    〔凭证：expand 160×3.1k=106.4% → 快 38%；DMA 656store+2load〕
- 正确性验收（对照腿必过）：canonical 输出对照 + recall_output_equal +
  cancel 后资源归零。〔凭证：W2 四步闭环〕

## 8. 计量口径（全腿共用）

- token 真值：/tokenize 端点实测或响应 usage 字段，**禁止估算**。
  〔凭证："w12345"≈5 tok/词、两位数≈2.9 tok/数，估错三次 400〕
- TTFT = 首 token − 提交；E2E = 完成 − 提交。流式取首 chunk，须开
  `stream_options.include_usage`（否则 usage 为 null）。
- 池用量**比 token 不比百分比**（block 粒度差会让百分比读数 ×2/×8）。
- /health 可能 200+空 body，勿当 JSON 解析。
- 计时一律服务端可核（driver 本地计时 + 引擎日志吞吐行交叉校验）。

## 9. 汇报纪律

- n≥2 才报差值；离群样本保留并说明（不悄悄丢弃）。
  〔凭证：A2 55.3s 离群标噪声窗口；B1 214.3s 判首跑暖机〕
- 无效数据（违反 §4-§7 有效判据）不入正文，附录可留并标"无效+原因"。
- 不可比数字不并列（五要素不全者分开各表）。
- 收益叙述必须能覆盖代价叙述（K>G 原则的推广）。
- 报告末尾固定小节："本轮偏离规范之处"。

## 10. prompt 设计规则

- 确定性生成要防周期碰撞：`i*P + j*Q mod M` 检查 M 与请求数的同余关系，或头部
  直接注入请求号（str(i) 开头）。〔凭证：i=100 与 i=0 同串〕
- prefix caching 重放效应：确定性 prompt 第二跑 TTFT 70s→1s。主动用于构造暖跑，
  **禁止把重放跑当首跑数据**。
- 并发腿用唯一 prompt（防共享前缀把"扩容"测成"共享"）；共享前缀是专门腿，单独设计。
